# ADR-005: Methodology-Driven Planning

> Version: 1.0
> Status: **Accepted**
> Builds on [ADR-004](ADR-004-execution-model.md). Resolves the open question
> it recorded. Amended by
> [ADR-006](ADR-006-plan-owns-its-governance.md): the plan, not the registry,
> owns the gates it was planned with, and the analysis no longer carries the
> work breakdown.

---

# Context

[ADR-004](ADR-004-execution-model.md) made execution *ordering* deterministic:
a dependency graph decided what ran when, and an unsatisfiable graph was
rejected rather than guessed at.

It left the more important half open. **The plan itself was still generated by
a language model.** The analysis step asked the model to decompose a mission
into deliverables, activities and capabilities, and whatever it returned became
the engagement. Two runs of the same mission produced different work.

That contradicted the platform's own stated thesis in
[03-methodologies.md](03-methodologies.md):

> The Workflow is deterministic. Artificial Intelligence generates the content
> of the deliverables. Hyperium determines the execution structure.

and its explicit prohibition in [01-vision.md](01-vision.md):

> Hyperium should automate methodologies. It should not invent them.

Until this was fixed, Hyperium was a well-engineered prompt chain. The
methodology — the thing [03-methodologies.md](03-methodologies.md) calls "one
of Hyperium's primary competitive advantages" — did not exist as code.

---

# Decision

## 1. A methodology authors the plan; the model writes the content

`MethodologyPlanner` builds the deliverables, activities, capability
requirements and dependencies for an engagement from a `Methodology`. It is
pure and deterministic: the same methodology and mission produce the same work
breakdown every time.

The model's job is now confined to what it is genuinely good at — writing the
content of each activity.

```
Mission ──> Analysis (understanding + recommendation)
        ──> Methodology ──> deterministic plan
        ──> Execution (model writes content)
```

## 2. Analysis is demoted from planner to advisor

The analysis step no longer decomposes anything. It produces a summary,
assumptions, risks, and a **recommended methodology** chosen from the
registry — it may not invent a key.

Consequently **a failed analysis no longer costs the engagement**. If the
provider is down or the response is unparsable, the engagement proceeds using
the methodology named on the mission or the configured default. Before this
change the same failure produced an empty plan and a vacuous success.

Methodology selection is: **the mission's explicit choice → the analysis
recommendation → the configured default.** If none yields a methodology,
planning fails loudly. There is deliberately no fallback to model-generated
planning; that is the behaviour this ADR removes.

## 3. Methodologies are authored data, not code

Methodologies and techniques are JSON under `methodologies/`, loaded by
`JsonMethodologyRepository`, and validated on load. A new methodology requires
no code change, satisfying [09-extensibility.md](09-extensibility.md).

JSON rather than YAML so that authoring a methodology does not add a parser
dependency to a platform whose only runtime dependency is an LLM client.

Validation is strict and happens once, at load, naming the file: duplicate
keys, unknown dependencies, self-dependencies, stage cycles, activities with no
capabilities, unknown technique references, and **dependencies that point at a
later stage** are all rejected. An authoring error must not surface halfway
through an engagement.

## 4. Techniques carry the consulting craft

A capability says *what* a resource can do. A `Technique` says *how* the work
is performed — stakeholder mapping, root-cause analysis, acceptance criteria.
Its guidance is layered onto the capability persona in the prompt.

This is the reusable practice a consultant should recognise as their own.

## 5. Stage ordering is expressed as activity dependencies

Rather than adding a second scheduler, the planner expands stage ordering into
ordinary activity edges: every activity in a stage waits on the terminal
activities of the stages it depends on. The existing topological sort then
enforces stage order, so there is only one scheduling mechanism to keep
correct.

## 6. The quality gate is the stage, not the deliverable

A `QualityGate` is declarative and checkable: human approval, a minimum word
count, required sections. **A model never decides whether a gate has passed** —
that would put it in charge of governance, which
[05-agents.md](05-agents.md) reserves for Hyperium.

Critically, **the review boundary moved from the deliverable to the stage.**
Deliverables within a stage are drafted together and reviewed together; they do
not gate each other. Work in the next stage cannot begin until the previous
stage's gate passes.

This was found by running a real engagement, not by reasoning: a deliverable
that depended on a sibling in the same stage stranded that stage half-finished,
because the sibling could not be approved until the stage was complete and the
stage could not complete until the sibling was approved. The 1.0 rule — that
cross-deliverable dependencies require approval — is retained only where there
is no stage to govern the boundary.

# Consequences

**Amended by [ADR-006](ADR-006-plan-owns-its-governance.md).** As first
implemented, the methodology's output was written back into `AnalysisResult`
and the gates were resolved from the registry at read time. Both are fixed;
decision 1 and decision 6 are otherwise unchanged.

**Positive**

- The plan is reproducible. The same mission and methodology always produce
  the same work.
- The platform's differentiator now exists as code rather than as a document.
- Methodologies can be authored, reviewed and versioned as data.
- Quality gates are enforceable and explainable — a stalled engagement names
  what is holding it.
- A provider outage during analysis is survivable.

**Negative**

- **A methodology is now required.** An engagement cannot be run without one.
  This is intended, but it is a hard break from 1.x behaviour.
- `required_sections` is a case-insensitive substring match against the
  generated document. It is crude: a live run produced a business case whose
  heading read "Recommendation" rather than "Recommendations" and the gate
  blocked the stage. The gate was behaving correctly and the document was
  arguably fine. Gate checks should stay few and forgiving until something
  better than substring matching exists.
- Gate authoring is fragile in one specific way: because `required_sections`
  is checked against *every* deliverable in a stage, adding a deliverable to a
  stage without the matching section will block it.
- Persisted plans gained a schema version (3). Older engagements do not load.

# Alternatives considered

**Keep model-generated planning, and validate the output against a
methodology.** Rejected: it keeps the non-determinism and adds a second place
where the work breakdown can disagree with itself. If the methodology is
authoritative enough to validate against, it is authoritative enough to plan
from.

**Let the model tailor a methodology per mission** — adding or dropping stages
based on context. Attractive, and probably right eventually. Rejected for now
because it reintroduces run-to-run variance through the back door, and the
value of determinism is not yet proven in practice. Worth revisiting once
several methodologies have run repeatedly.

**Python-authored methodologies.** Rejected: it makes every new methodology a
code change, contradicting the extensibility rule, and prevents a consultant
who is not a programmer from reading or authoring one.

**Gate on the deliverable rather than the stage.** This is what 1.0 did, and it
deadlocks the moment two deliverables in a stage depend on each other. See
decision 6.

---

# Open questions

- Should a methodology be able to mark stages or deliverables as optional, so
  a small engagement can skip work without a separate methodology?
- `required_sections` needs something better than substring matching —
  probably a structural check against the deliverable's declared sections.
- Deliverables are Markdown only. The formats clients actually receive — Word,
  PowerPoint, BPMN — remain unbuilt.
- Only one LLM provider exists. The abstraction has never been exercised
  against a second one.
