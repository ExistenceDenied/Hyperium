# Hyperium Domain Model

> Version: 1.0

---

# Purpose

The Domain Model defines the core business concepts of Hyperium.

Every component within the platform should be built around these concepts.

The domain model represents **what Hyperium is**, independent of any implementation or programming language.

---

# Domain Overview

```
Methodology

        ▼

        ▼
```

---

# Methodology

## Purpose

A methodology defines **how a consultancy engagement is performed**.

It describes the recommended approach for solving a particular type of problem.

## Examples

- Business Analysis
- Enterprise Architecture
- Software Delivery
- Compliance Assessment
- Data Migration

A methodology owns one or more workflows.

---

# Workflow

## Purpose

A workflow defines the sequence of activities required to execute a methodology.

A workflow is deterministic.

It should not be generated by AI.

## Contains

- stages
- dependencies
- completion rules

---

# Stage

## Purpose

A stage groups related work items.

Examples:

- Discovery
- Analysis
- Design
- Implementation
- Validation

Stages improve readability and reporting.

---

# Work Item

## Purpose

A Work Item represents a single unit of work.

It is the smallest schedulable activity within Hyperium.

## Examples

- Interview stakeholders
- Write requirements
- Produce BPMN model
- Review architecture

Each Work Item is assigned to exactly one agent.

---

# Agent

## Purpose

An Agent is a specialist capable of executing a Work Item.

Agents represent consulting roles.

Examples:

- Business Analyst
- Solution Architect
- Enterprise Architect
- Developer
- Tester
- Reviewer

Agents create or improve deliverables.

---

# Deliverable

## Purpose

A Deliverable represents business value produced during a project.

Clients ultimately receive deliverables.

## Examples

- Requirements Specification
- Architecture Document
- BPMN Model
- Business Case
- Test Report

Every deliverable has an owner.

Every deliverable maintains version history.

---

# Deliverable Version

## Purpose

Every modification of a deliverable creates a new version.

Versions allow quality evolution to be tracked over time.

A version contains:

- filename
- creation date
- author
- review score
- review summary

---

# Review

## Purpose

A Review evaluates the quality of a deliverable version.

A review may:

- approve
- request improvements
- reject

Reviews may generate additional work items.

---

# Project

## Purpose

A Project represents a consultancy engagement.

A project owns:

- methodology
- workflow
- work items
- deliverables
- reviews
- project knowledge

The project is the highest-level business entity within Hyperium.

---

# Relationships

A Project follows one Methodology.

A Methodology defines one or more Workflows.

A Workflow consists of one or more Stages.

Each Stage contains Work Items.

Each Work Item is executed by one Agent.

Each Work Item produces or updates Deliverables.

Each Deliverable consists of one or more Versions.

Each Version may receive one or more Reviews.

Reviews may generate additional Work Items.

---

# Guiding Principle

Everything in Hyperium should ultimately support one of these domain concepts.

If a new feature cannot be mapped onto the domain model, its design should be reconsidered.
